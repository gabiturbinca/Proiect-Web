Rezumat

Documentul specifică cerințele software ale aplicației Web GiW (Gift Web Manager), un asistent digital care recomandă cadouri în funcție de preferințe, circumstanță, context social, buget, ofertant și anotimp. Sunt descrise interacțiunea cu utilizatorul, cerințele funcționale și non-funcționale, deciziile de arhitectură și etapele dezvoltării, conform machetei IEEE pentru specificarea cerințelor.

1. Introducere

Scop. GiW asistă utilizatorul în alegerea unui cadou pentru o persoană sau un grup, filtrând și ordonând un catalog de produse după buget, categorie, marcă, ocazie și relația socială cu destinatarul. Sistemul oferă și recenzii, simularea comenzii (cu expediere anonimă opțională) și un modul de administrare cu rapoarte.

Convenții. Cerințele funcționale sunt identificate prin RF-x.y, cele non-funcționale prin RNF-x.y. Termenii definiți apar în stil evidențiat și sunt reluați în glosar; identificatorii tehnici apar monospațiat.

Domeniu. Aplicație Web de sine stătătoare, accesibilă din browser. Serviciile externe (DummyJSON, Unsplash) sunt opționale — folosite la popularea catalogului și a imaginilor — iar indisponibilitatea lor nu afectează funcțiile esențiale.

2. Descriere generală

2.1 Perspectiva produsului

Produs nou, construit ca aplicație bazată pe servicii: un backend PHP expune un API REST, iar un client (HTML/CSS/JavaScript vanilla) îl consumă asincron prin Ajax. Persistența se face în PostgreSQL.

2.2 Funcțiile produsului

La nivel înalt, sistemul oferă:

  • gestiunea contului — înregistrare, autentificare, schimbarea și resetarea parolei;
  • recomandarea de cadouri pe baza unui formular de criterii;
  • răsfoirea catalogului și vizualizarea detaliilor unui cadou, cu cadouri înrudite;
  • recenzii și note pentru cadouri;
  • plasarea și urmărirea comenzilor, cu expediere anonimă opțională;
  • administrarea aplicației — CRUD pe catalog, gestiunea comenzilor și a utilizatorilor, rapoarte, import/export, integrări externe.

2.4 Mediul de operare

Server PHP 8.3 pe Apache, PostgreSQL, containerizat cu Docker și desfășurat pe Render. Client: orice browser modern cu suport pentru fetch, <template> și cookie-uri. Comunicație peste HTTPS.

2.5 Constrângeri de proiectare

  • Fără framework la client sau server (cerință) — router, container DI, middleware și validare implementate manual.
  • Arhitectură bazată pe servicii Web, cu invocare asincronă Ajax.
  • HTML și CSS valide W3C; design responsive.
  • Cod-sursă sub licență liberă; conținut conform Creative Commons.

2.6 Presupuneri și dependențe

  • Utilizatorul are JavaScript activat, pentru conținutul dinamic încărcat prin Ajax.
  • Serviciile externe DummyJSON și Unsplash sunt disponibile la momentul importului administrativ; altfel, funcțiile esențiale rămân operaționale.
  • Aplicația rulează peste HTTPS, condiție pentru securitatea cookie-urilor.

3. Interacțiunea cu utilizatorul

Interfața este un set de pagini responsive randate server-side și îmbogățite cu JavaScript, care consumă API-ul asincron prin Ajax. Navigarea se face printr-o bară superioară al cărei conținut se adaptează rolului: vizitatorul vede „Search gift”, „Login” și „Register”; utilizatorul autentificat vede în plus „My orders” și „Change password”; administratorul vede și intrarea „Admin”. Pe ecrane înguste meniul colapsează într-un buton hamburger accesibil (aria-expanded/aria-controls).

3.1 Convenții de interacțiune și feedback

  • Validare în doi pași. Formularele validează intrarea pe client (tipuri, câmpuri obligatorii, interval de buget) înainte de trimitere; serverul revalidează și întoarce erori structurate pe câmp (cod 422).
  • Feedback explicit. Fiecare acțiune confirmă rezultatul prin mesaj de succes sau eroare; acțiunile distructive sau sensibile (anulare comandă, resetare parolă, aprobare/respingere cerere) cer confirmare prealabilă.
  • Paginare. Listele lungi (rezultate, cadouri, comenzi, utilizatori, cereri) oferă navigare înainte/înapoi, cu butoanele dezactivate la capete.
  • Degradare grațioasă. La eșecul unei cereri, doar zona afectată afișează un mesaj prietenos, fără a bloca restul paginii.
  • Sesiune. Autentificarea se transmite printr-un cookie HttpOnly cu token JWT; cererile de modificare poartă automat antetul X-CSRF-Token. Delogarea invalidează sesiunea.

3.3 Fluxul principal: descoperirea unui cadou

Fluxul central pornește din formularul de recomandare: utilizatorul stabilește intervalul de buget și selectează categoriile, mărcile și tag-urile dorite. La trimitere, aplicația cere API-ului lista de cadouri candidate, le ordonează după scor și le afișează paginat ca un set de carduri (imagine, titlu, descriere, preț). Selectarea unui card deschide pagina cadoului, de unde utilizatorul autentificat poate lăsa o recenzie sau iniția o comandă; tot acolo sunt sugerate cadouri înrudite, permițând explorarea în continuare. Astfel, interacțiunea acoperă întregul parcurs: de la criterii → rezultate → detaliu → acțiune (comandă/recenzie).

4. Cerințe funcționale

4.1 Autentificare și cont

RF-1.1 Înregistrare cu nume, e-mail și parolă, cu unicitatea numelui și e-mailului (conflict 409 altfel).

RF-1.2 Autentificare cu nume sau e-mail + parolă; la succes se emit token JWT (cookie) și token CSRF.

RF-1.3 Limitarea autentificării la 5 încercări / 5 minute per adresă IP.

RF-1.4 Schimbarea parolei de către utilizator; token-urile emise anterior devin invalide.

RF-1.5 Trei fluxuri de resetare: cerere aprobată de admin; resetare directă de către admin; schimbare forțată la prima autentificare cu parolă temporară.

RF-1.6 Răspuns identic la cererile de resetare, indiferent dacă identificatorul există (anti-enumerare).

4.2 Motorul de recomandare

RF-2.1 Formular de criterii: interval de buget, categorii, mărci, tag-uri.

RF-2.2 Filtrarea candidaților și ordonarea după un scor compus (potrivire buget, categorie, marcă, popularitate, context, circumstanță).

RF-2.3 Rezultate paginate.

RF-2.4 Afișarea cadourilor înrudite (similare, care se potrivesc împreună, care includ).

4.3 Recenzii

RF-3.1 Citirea publică a recenziilor unui cadou.

RF-3.2 Adăugarea, modificarea și ștergerea propriei recenzii (notă 1–5 + comentariu), cel mult una per cadou.

4.4 Comenzi și simulare expediere

RF-4.1 Plasarea unei comenzi cu cantitate, adresă și destinatar.

RF-4.2 Marcarea comenzii ca anonimă.

RF-4.3 Vizualizarea propriilor comenzi și anularea în stările permise.

RF-4.4 Ciclu de viață controlat al statusului, cu respingerea tranzițiilor nepermise.

4.5 Administrare

RF-5.1 CRUD cadouri și categorii, inclusiv încărcarea și ștergerea imaginii unui cadou.

RF-5.2 Lista utilizatorilor și resetarea parolei oricăruia.

RF-5.3 Vizualizarea tuturor comenzilor și schimbarea statusului.

RF-5.4 Gestiunea cererilor de resetare în așteptare (aprobare/respingere).

RF-5.5 Validarea tipului real (MIME) la încărcarea imaginilor și securizarea numelui fișierului.

4.6 Rapoarte

RF-6.1 Rapoarte privind cadourile recomandate și cele alese, filtrabile pe categorie și interval de timp.

RF-6.2 Generare în formatele HTML, JSON, CSV și PDF.

4.7 Import și export

RF-7.1 Export de cadouri și categorii în CSV și JSON.

RF-7.2 Import din aceleași formate, compatibil cu exportul (round-trip).

4.8 Integrări externe

RF-8.1 Import unic de produse din DummyJSON, cu creare automată a mărcilor/categoriilor lipsă, idempotent și tolerant la erori per-produs.

RF-8.2 Obținerea automată a unei imagini din Unsplash pentru categoriile noi fără imagine; eșecul serviciului nu blochează importul.

5. Cerințe non-funcționale

5.1 Securitate

RNF-1.1 Parolele stocate doar ca hash bcrypt; verificare în timp constant, cu hash fals la eșec pentru uniformizarea timpului de răspuns.

RNF-1.2 Toate interogările SQL parametrizate — prevenire a injecției SQL.

RNF-1.3 Randarea datelor prin textContent (client) și htmlspecialchars (server) — prevenire XSS.

RNF-1.4 Protecție CSRF prin tiparul double-submit cookie; JWT în cookie HttpOnly + SameSite=Lax.

RNF-1.5 Autorizare prin lanț de middleware (autentificare → CSRF → rol admin); invalidarea sesiunilor la schimbarea parolei.

5.2 Performanță

RNF-2.1 Listări paginate.

RNF-2.2 Indecși dedicați pentru interogările frecvente (ex. rate limiting).

RNF-2.3 Cache pe disc pentru răspunsurile serviciilor externe.

5.3 Atribute de calitate

RNF-3.1 Mentenabilitate: cod modular, stratificat, cu șabloane de proiectare și responsabilități separate.

RNF-3.2 Robustețe: handler global de excepții care mapează tipurile de erori pe coduri HTTP; erorile serviciilor externe sunt izolate.

RNF-3.3 Accesibilitate: HTML semantic, atribute ARIA, contrast adecvat.

7. Evoluția arhitecturii și a implementării

Sistemul a fost construit incremental, pe etape de funcționalitate. Mai jos, evoluția surprinde nu doar ce s-a implementat, ci și cum a crescut arhitectura — ce strat sau șablon a fost introdus la fiecare pas.

  1. Fundația de date și structura proiectului. S-a fixat separarea dintre rădăcina publică și codul de aplicație și schema relațională PostgreSQL: entitățile centrale (utilizatori, cadouri, categorii, mărci), taxonomia (tag-uri, circumstanțe, contexte) și tabelele de legătură. Modelul de date a stabilit de la început relațiile many-to-many și constrângerile de integritate.
  2. Stratul de autentificare și securitate. Aici a luat formă arhitectura stratificată: front controller, router manual și container de injecție a dependențelor prin reflexie. S-au introdus lanțul de middleware (autentificare → CSRF → rol), JWT în cookie HttpOnly, tiparul CSRF double-submit și rate limiting-ul la autentificare. Securitatea a devenit un strat transversal, nu cod împrăștiat prin controllere.
  3. Logica de business: recomandare, recenzii, comenzi. S-a consolidat separarea Controller → Service → Repository. Motorul de recomandare a fost construit cu șabloanele Strategy + Composite — fiecare criteriu de scoring (buget, categorie, marcă, popularitate, context, circumstanță) este o regulă independentă, compozabilă. Recenziile și comenzile au adăugat reguli de domeniu (o recenzie per utilizator per cadou; ciclul de viață controlat al comenzii).
  4. Modulul de administrare și schimbul de date. A apărut panoul de administrare (CRUD pe catalog, gestiunea comenzilor și a utilizatorilor) și randarea server-side conștientă de rol (meniul adaptat prin decodarea JWT). S-au adăugat exportul/importul în formate deschise (CSV/JSON) și relațiile de cadouri înrudite.
  5. Rapoarte prin Factory. Generarea rapoartelor a fost izolată într-o fabrică ce serializează același set de date în HTML, JSON, CSV și PDF; adăugarea unui format nou nu afectează logica existentă.
  6. Resetarea parolei și revocarea sesiunilor. S-au implementat cele trei fluxuri de resetare și invalidarea token-urilor prin password_changed_at. Arhitectura de autentificare a trecut astfel de la „pur stateless” la hibrid — o verificare în baza de date per cerere permite revocarea sesiunilor la schimbarea parolei.
  7. Livrare și normalizarea timpului. Containerizare Docker și desfășurare pe Render, cu încărcare tolerantă a configurației (mediul containerului, apoi opțional fișierul .env). Migrarea tuturor coloanelor temporale la TIMESTAMPTZ a eliminat o clasă de erori de fus orar la compararea timpilor.
  8. Integrări cu servicii externe. S-au adăugat serviciile pentru Unsplash și DummyJSON, fiecare izolat prin ExternalServiceException și tratat centralizat (cod 502 + mesaj generic). Importul DummyJSON populează catalogul (find-or-create pe mărci și categorii, idempotent și tolerant la erori), iar categoriile noi primesc automat o imagine din Unsplash.

Glosar

JWT
JSON Web Token — mecanism de autentificare bazat pe token semnat.
CSRF
Cross-Site Request Forgery — prevenit prin tiparul double-submit cookie.
DTO
Data Transfer Object — obiect imutabil pentru transferul datelor.
Middleware
Filtru compozabil aplicat cererii înainte de controller.
Repository
Strat care izolează accesul la baza de date.
SSR
Server-Side Rendering — randarea HTML pe server înainte de livrare.
